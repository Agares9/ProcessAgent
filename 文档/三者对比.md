# 设计思路对比

## 1. 几个之前项目经验

三个项目都采用“LLM 理解问题、调用知识或工具、生成结果”的基本模式，但 Agent 的组织方式、控制边界和调度机制不同。

| 维度 | 项目1 | 项目2 | 项目3 |
|---|---|---|---|
| 核心思想 | 固定、受治理的问答 DAG | 意图驱动的 Plan-and-Execute | Skills-Agent 两层架构与 Swarm |
| 主控制者 | Python Orchestrator | IntentionAgent + OrchestrationAgent | SwarmCoordinator + LeadAgent |
| Agent 划分 | 按处理阶段划分 | 按用户意图和业务能力划分 | 按医疗专业角色划分 |
| 调度方式 | 固定顺序、明确降级 | 动态计划和优先级调度 | 单 Agent 或去中心化 Swarm |
| 并行方式 | 部门 Agent 并行，主链相对固定 | 同优先级并行，不同优先级串行 | Agent 自主认领任务并行执行 |
| Skills | 受控工作流、规则和程序性知识 | 子 Agent 插件化为 Skills | 专业 Agent 共享原子 Skills |
| 工具选择 | Orchestrator 控制较强 | 编排器按意图选择插件 | Agent Loop 自主选择 Skill |
| 结果校验 | Answer 后执行 Verifier | 主要依赖计划完成和结果汇总 | 约束校验、输出校验和自动修复 |
| 状态与记忆 | 事实平面与五类记忆 | 两层记忆与计划状态 | SharedContext 事件与短期/长期记忆 |
| 自我改进 | Observe/Reflect/Adapt/Deploy Loop | 动态注册和插件扩展 | Agent 记忆、Skill 扩展和 Swarm 协作 |
| 可预测性 | 高 | 较高 | 相对较低 |
| 适合场景 | 知识治理和可靠问答 | 多意图任务规划 | 开放式多专家协作 |

## 2. 文枢

文枢的 Agent 主要按照问答处理阶段划分：

```text
Intent
→ Rewrite
→ Retrieval
→ Answer
→ Verify
→ Feedback
```

Python Orchestrator 是唯一控制平面。Agent 不能绕过权限、事实检索、记忆规则、策略治理和验证流程。

### 优点

- 流程稳定，执行路径明确。
- 引用、事实和记忆边界清晰。
- 容易测试、审计、降级和回放。
- 适合正式知识库问答和文档治理。

### 不足

- 面对复杂场景时，动态任务拆解能力较弱。
- 原有部门 Agent 和学校领域模型不适用于制造业。
- 固定 DAG 需要引入动态计划能力才能支持复杂解决方案。

## 3. 项目6：差旅助手

项目6采用意图识别和 Plan-and-Execute：

```text
IntentionAgent
→ OrchestrationAgent
→ 生成计划
→ 同优先级任务并行
→ 后续优先级任务串行
→ 汇总结果
```

系统可以识别多个意图，根据意图动态选择 Skill 插件。`LazyAgentRegistry` 在启动时读取插件元数据，执行时再加载具体能力。

### 优点

- 适合复杂问题和多意图拆解。
- 任务依赖、优先级和并行关系明确。
- 新能力可以通过插件扩展。
- 相比自由 Swarm，执行过程更可控。

### 不足

- 原始 Agent、Prompt 和字段属于差旅领域，不能直接复制。
- 原项目使用 AgentScope，不应作为 ProcessAgent 的第二套主运行时。
- 证据治理、引用校验和事实边界不如文枢完整。

## 4. MediX 医疗助手

MediX 包含单 Agent 和 Swarm 两条执行路径：

```text
简单问题
→ 单个专业 Agent
→ Agent Loop
→ Skills

复杂问题
→ SwarmCoordinator
→ LeadAgent 拆解
→ Agent 自主认领任务
→ SharedContext 汇总
```

专业 Agent 共享原子 Skills，LLM 在 Agent Loop 中自主选择需要调用的 Skill。复杂问题通过 SharedContext 和事件机制进行协作。

### 优点

- Skills/function calling 实现较成熟。
- Agent 调用工具灵活。
- 具备调用次数限制、约束、状态事件和进度能力。
- 适合开放式探索和多专家协作。

### 不足

- Swarm 的完成时间和执行路径不稳定。
- 多个 Agent 可能重复分析相同内容。
- 复杂问题可能触发较多 LLM 调用并导致超时。
- 不适合作为要求稳定、可复算的制造决策主控制器。

## 5. 共同点

三个项目都具备以下思想：

- 使用 LLM 理解用户问题。
- 将知识检索或程序能力提供给 Agent。
- 支持一定程度的任务路由和结果汇总。
- 保存会话状态或长期记忆。
- 通过结构化输出降低自然语言结果的不确定性。
- 将 Agent 推理与确定性程序能力进行组合。

它们的关键区别不在于是否使用 Agent，而在于谁掌握控制权、任务如何拆解、工具如何授权，以及结果如何验证。

## 6. ProcessAgent 的采用方式

ProcessAgent 不完整复制任何一个项目，而是明确组合三者的优势：

```text
文枢
→ 唯一控制平面、RAG、事实治理、验证、记忆和 API

项目6
→ 意图识别、计划生成、任务依赖和优先级并行

MediX
→ Skill 协议、调用约束、超时降级和进度事件
```

最终运行结构：

```text
Python Harness
→ ManufacturingIntentAgent
→ EnterpriseContextAgent
→ LeadAgent 生成受控计划
→ 动态场景分析任务调用 Skills
→ VerifierAgent
→ ExecutiveSynthesisAgent
```

### 固定流程 Agent

- `ManufacturingIntentAgent`：识别目标、对象、约束和缺失信息。
- `EnterpriseContextAgent`：整理用户提供的企业、工厂和工艺上下文。
- `LeadAgent`：生成任务计划、依赖和优先级。
- `VerifierAgent`：校验证据、引用、数字、假设和冲突。
- `ExecutiveSynthesisAgent`：汇总通过验证的分析结果。

### 动态场景分析

降碳、质量、成本、产能、设备、材料和合规等只是动态任务角色，不分别建立长期固定 Agent。LeadAgent 根据具体问题创建任务，并为任务分配允许调用的 Skills。

### 明确不采用

- 不把 AgentScope 引入为第二套主运行时。
- 不使用自由 Swarm 作为制造决策主流程。
- 不按每一种示例问题建立固定专业 Agent。
- 不迁移医疗或差旅领域的 Prompt、数据和业务规则。
- 不允许 Agent 绕过 RAG、证据校验和确定性计算服务生成精确结论。

## 7. 结论

ProcessAgent 应以文枢 Python Harness 为主框架，使用项目6的 Plan-and-Execute 完成动态任务规划，并吸收 MediX 的 Skills 与运行约束。固定 Agent 负责流程治理，专业分析按问题动态生成任务，从而兼顾稳定性、扩展性和复杂制造场景的分析能力。

# agent功能梳理

| Agent                    | 作用                                                         | 是否使用知识库               |
| ------------------------ | ------------------------------------------------------------ | ---------------------------- |
| ManufacturingIntentAgent | 识别用户问题属于制造业分析、能力询问、闲聊还是范围外问题；判断复杂度、目标、行业、工艺、设备和缺失信息 | 否                           |
| EnterpriseContextAgent   | 将用户在对话中提供的企业、工厂、设备、工艺、产量、能耗等信息整 理成当前问题上下文 | 否                           |
| LeadAgent                | 针对标准和复杂问题拆解任务，决定需要检索、计算、方案比较、适用 性判断等工作 | 间接，通过任务规划调用 Skill |
| VerifierAgent            | 检查任务结果、证据来源、文档编号、页码、原文片段和计算结果是否完整可靠 | 不主动检索，负责校验结果     |
| OrchestratorAgent        | 统一总调度，组织任务执行结果，调用最终大模型生成自然语言回答，并决定回答重点、长度和是否提示补充信息 | 间接，汇总检索和 Skill 结果  |

# skills功能梳理

### 1. 知识检索类

 

| Skill                          | 作用                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| search_manufacturing_knowledge | 从 SQLite 文档元数据和 Chroma 向量库检索制造业标准、指南和技术资料 |
| search_case_studies            | 检索制造业案例，优先筛选 doc_type=case_study 的文档          |
| get_document_evidence          | 根据 chunk_id 获取原始摘录、文档、页码和来源信息             |

```
  典型流程：

  用户问题
  → 向量检索
  → 返回 Chunk
  → 根据 Chunk 获取原始证据
  → 交给 Verifier 检查
```

  - 不让 Agent 直接操作数据库
  - 不让模型自己编造来源
  - 返回 source_id/chunk_id/page_start/page_end
  - 证据可以回溯到原始文档

```
  目标是让系统理解：
```

  - 用户自然语言
  - EnterpriseContextAgent
  - 当前会话记忆
  - 可选的 profile JSON

  ### 4. 方案比较和计算类

| Skill                        | 作用                                                   |
| ---------------------------- | ------------------------------------------------------ |
| compare_technical_options    | 比较多个技术方案的成本、收益、风险、适用条件和实施难度 |
| calculate_project_financials | 计算投资、年度节省、回收期、净现值和敏感性             |
| check_constraint_compliance  | 检查方案是否满足预算、回收期、产能、质量安全和法规约束 |

```
  技术方案比较应输出结构化结果：

  {
    "options": [
      {
        "name": "变频改造",
        "capex": 800000,
        "annual_saving": 260000,
        "payback_years": 3.08,
        "risk": "中",
        "applicability": "适合负荷波动设备"
      }
    ],
    "recommended_option": "变频改造",
    "reason": "在预算和改造窗口约束下综合得分最高"
  }

财务计算 Skill 必须是确定性代码，不应让 LLM 直接计算：

  年度节省 = 节能量 × 能源单价
  回收期 = 初始投资 ÷ 年度净收益
  净收益 = 年度节省 - 年运维成本

```



  ### 5. 验证和治理类

| Skill                       | 作用                                     |
| --------------------------- | ---------------------------------------- |
| verify_citations            | 检查结论是否有有效来源、Chunk 和页码支撑 |
| check_constraint_compliance | 检查最终方案是否违反用户约束             |
|                             |                                          |

```
  当前 VerifierAgent 已经能做部分确定性检查：

  - 任务是否失败
  - 是否有 source_id
  - 是否有 chunk_id
  - 是否有页码
  - 摘录是否为空
  - 是否重复使用同一证据

  后续将这些能力统一封装成 Skill，便于：

  VerifierAgent
  → 调用 verify_citations
  → 调用 check_constraint_compliance
  → 输出统一验证结果
```



 ## 当前设计如何控制速度

```
  simple
  → 跳过 LeadAgent
  → 只做一次检索

  standard
  → 保留 LeadAgent
  → 执行有限任务

  complex
  → 执行完整分析
  → 无依赖任务并行
```

  因此不能让 LeadAgent 每次都规划所有 Skill，而应该让它根据复杂度选择：

| 复杂度   | 调用的 Skill                                             |
| -------- | -------------------------------------------------------- |
| simple   | 一个知识检索 Skill                                       |
| standard | 知识检索 + 案例检索 + 适用性判断                         |
| complex  | 检索、参数、适用性、方案比较、财务、碳排、约束和引用验证 |

```
需要先说明的是，目前检索到的资料主要涉及汽轮机、抽油机、热泵等领域的节能改造案例，与注塑机直接相关的针对性证据较少。因此，以下分析主要基于注塑行业通用的能耗管理逻辑，并结合现有资料中可参考的节能思路，供您结合工厂实际情况排查。

---

### 一、能耗上升的常见原因排查方向

建议从以下五个维度逐项排查，优先检查数据记录和现场可观察项：

**1. 生产排程与设备利用率变化**
- 检查近期订单结构是否变化（如小批量、多品种切换增多），导致注塑机频繁空转或待机时间延长。
- 确认每台机的实际运行小时数、待机时间占比是否较之前增加。

**2. 设备状态与维护情况**
- 注塑机液压系统、螺杆、料筒等部件磨损会导致效率下降、能耗上升。检查近期是否有设备出现异常振动、噪音或温升。
- 确认液压油是否到期未更换、油温是否过高（油温升高会显著增加液压泵功耗）。
- 检查加热圈、热电偶是否老化或失效，导致加热效率降低、保温时间延长。

**3. 工艺参数调整**
- 对比近期与之前的工艺参数记录（如料温、模温、注射压力、保压时间、冷却时间等），确认是否有调整导致能耗增加。
- 检查模具冷却水路是否堵塞或结垢，影响冷却效率，延长成型周期。

**4. 原材料批次变化**
- 不同批次的塑料原料（如熔指、含水率差异）可能需要更高的加工温度或更长的干燥时间，间接推高能耗。

**5. 环境因素**
- 夏季环境温度升高，会导致设备散热变差、冷却系统负荷增加，从而推高总能耗。可对比去年同期数据判断是否存在季节性因素。


### 二、建议的排查步骤

1. **建立能耗基线**：调取近6-12个月每台注塑机的电表数据，按“单件产品能耗（kWh/件）”或“每吨原料能耗”计算单位能耗，找出能耗上升是从哪个月、哪几台设备开始。
2. **现场巡检**：重点检查液压系统油温、加热系统工作状态、冷却水系统流量与温度。
3. **数据对比**：将近期单位能耗与去年同期、上季度进行对比，排除季节性影响。
4. **记录分析**：核对生产排程记录、设备维修记录、工艺参数变更记录，找出与能耗上升时间点吻合的变动。


### 三、关于节能改造的参考信息

虽然现有资料中没有注塑机直接相关的案例，但其中关于**设备运行效率提升**的思路可供参考。例如，资料中提到汽轮机变工况运行改造技术，通过重新设计运行参数、优化通流结构，可使机组运行效率不低于出厂新机设计值，节能效率约6%~10%（来源：b1bc415a07a62bd4，第4页）。这一思路的核心是**让设备运行参数与实际工况匹配**，对注塑机而言，可类比为：

- 检查注塑机电机是否长期处于“大马拉小车”状态（即电机功率远大于实际负载需求），可考虑加装变频器或伺服节能改造。
- 优化加热系统保温，减少热量散失。

但请注意，上述改造效果为其他行业的案例数据，**不能直接作为您工厂的预期节能效果**，具体收益需根据您工厂的实际工况评估。


### 四、需要您补充的信息

为了更精准地定位问题，建议您提供以下数据（如有）：

1. 能耗上升的具体数值和起始时间（如“近3个月总用电量环比增加15%”）。
2. 同期产量变化情况（产量是否同步增加）。
3. 近期是否有设备维修、工艺调整、原料更换等事件。
4. 是否有分设备或分车间的电表计量数据。
```
