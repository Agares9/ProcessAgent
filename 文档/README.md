# 数据来源

目前知识库中的文档来源主要包括以下几类：

  - **国家发展和改革委员会（发改委）：**主要提供节能降碳政策、产业规划、重点行业行动方案和能效管理要求。
  - **工业和信息化部（工信部）：**主要提供制造业绿色发展、工业节能、技术改造、绿色工厂和行业规范文件。
  - **生态环境部：**主要提供污染物排放、碳排放、清洁生产和环保合规相关政策与标准。
  - 欧盟联合研究中心（JRC）：发布各行业最佳可行技术参考文件（BREF），涵盖钢铁、化工、表面处理、废处理等工艺的排放和能效要求
  - 中国节能协会、行业协会及专业机构：提供行业指南、技术路线、能效评价方法和应用案例。
  - **美国能源部 DOE Better Plants 等国际机构**：提供工业节能案例、技术改造经验和企业实践数据。
  - 企业和项目案例资料：用于补充具体工艺、设备改造、节能效果和实施条件，但只能作为参考，不能直接等同于当前企业结果。

  简单来说，知识库同时包含：

  政策文件
  + 国家和行业标准
  + 技术指南
  + 节能降碳案例
  + 制造企业实践资料

  其中，发改委、工信部、生态环境部和国家标准体系属于政策与权威规范来源；行业协会、DOE 和企业案例主要用于补充技术应用和实
  践经验。

# 文档更新机制

原本预计完成文档增加的功能，已经完成了核心能力，但还没有做到完整的自动化闭环。

  已经做到的部分

  1. 文件哈希去重
      - 对原始文件计算 SHA-256。
      - 相同文件重复入库时会拒绝。
      - 对分块内容也保存 content_hash，可以识别重复分块。

  2. 文档版本链
      - 同一标题或同一逻辑文档再次导入时，会生成新版本。
      - 新文档保存 supersedes，指向旧版本。
      - 版本号自动递增，例如 1.0 → 1.1。

  3. 旧版本归档
      - 新版本入库完成后，旧版本标记为 archived。
      - 检索默认只使用 active 文档，避免新旧内容同时参与回答。

  4. 向量重新生成
      - 支持对文档重新切分、重新生成向量并更新向量状态。
      - 文档和向量分别记录状态，例如 vector_status=ready。

  5. 关联记忆失效
      - 如果组织记忆引用的文档被归档或替换，相关记忆会被标记为 stale。
      - 后续不会继续把已经失效的组织记忆当作有效事实使用。

  6. 来源追踪
      - 检索结果保留文档 ID、版本、分块 ID、页码和原文片段。
      - 回答可以追溯到具体文档版本。

  7. 制造业文档导入检查
      - manufacturing_importer.py 已支持 manifest、重复文档和重复分块检测。
      - 已整理 PDF 可以按结构化格式进入 SQLite 和 Chroma。

  还没有完全做到的部分

  1. 没有自动监控文件夹
      - 目前不是把 PDF 放入目录后自动发现和更新。
      - 仍需要手动运行导入脚本。

  2. 没有完整的增量更新任务
      - 当前主要是“发现后重新导入”。
      - 还没有自动比较旧文档和新文档，只更新发生变化的章节或分块。

  3. 没有完善的文档状态机
      - 目前有 active、archived、deleted 等状态，但还缺少完整的：
          - 待审核
          - 审核中
          - 发布
          - 失效
          - 驳回
          - 定时复审

  4. 没有自动识别官方文档失效
      - 还不能自动判断标准是否废止、替代或过期。
      - 发布日期、实施日期、废止日期、替代标准 还需要更完整的元数据模型。

  5. 没有后台异步更新队列
      - 文档解析、切分、Embedding、向量更新还没有完整接入后台任务队列。
      - 大批量文档更新时，尚未形成可查看进度、失败重试和断点恢复的流程。

  6. 缺少版本差异报告
      - 目前能知道新版本替代旧版本。
      - 但还不能自动生成“新增了什么、删除了什么、哪些参数发生变化”的差异报告。

  7. 缺少更新后的质量评估
      - 文档更新后还没有自动重新执行检索命中率、引用完整性和回答质量评估。

  当前完成度判断

  - 文档版本、去重、归档、来源追踪：约 70%–80%
  - 文档自动更新和增量索引：约 40%
  - 文枢式完整文档治理闭环：约 50%–60%

  也就是说，我们已经具备了文枢机制的核心骨架，尤其是：

  文件去重
  → 版本生成
  → 新旧版本关联
  → 旧版本归档
  → 记忆失效
  → 向量更新
  → 来源追踪

  但目前还不是“目录有文件变化，系统自动完成检测、审核、解析、增量入库、质量评估和发布”的完整自动化系统。

# 制造业 PDF 知识库处理

## 本地 RAG 入库

`manufacturing-data/` 中的资料已经完成解析和分块。本地方案使用 SQLite 保存文档与 Chunk，
使用 Chroma 保存向量，Embedding 使用本地 `BAAI/bge-small-zh-v1.5`，不需要 Docker。

```powershell
conda activate medix-swarm
cd D:\workfile\ProcessAgent\backend

python -m scripts.import_manufacturing_rag --source ../manufacturing-data --dry-run
python -m scripts.import_manufacturing_rag --source ../manufacturing-data
python -m scripts.query_local_rag "如何降低工业压缩空气系统的能源浪费"
```

持久化文件位于 `local-data/`，该目录不会自动提交到 Git，。重复执行导入命令会按 `doc_id` 和
`chunk_id` 覆盖更新，不会重复累积。

原始资料位于 `文档/`，保持不变。处理输出使用 `manufacturing-data/`：

`raw/`（建议复制或软链接原始 PDF）、`parsed/`（逐页原始提取）、`normalized/`（Markdown）、`chunks/`（JSONL）、`manifests/`、`reviewed/`、`rejected/`。

先运行少量样本：

```powershell
python scripts/pdf_pipeline.py --sample --input 文档 --output manufacturing-data
```

也可显式传入 PDF。脚本不会默认批量扫描全部文件；PyMuPDF 提取为空的页面标记为 `needs_ocr`，只有传入 `--ocr-command` 才会调用 OCR。来源 URL、许可、工艺和案例字段默认为待人工确认。
